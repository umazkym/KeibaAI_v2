## 🏷️ モデル命名規則

### 基本フォーマット

```
{type}_{version}_{variant}_{training_period}
```

### 各要素の定義

#### 1. type（モデルタイプ）

| タイプ | 説明 | 例 |
|--------|------|-----|
| `mu` | μモデル単体 | `mu_v1.0_base_2020-2023` |
| `sigma` | σモデル単体 | `sigma_v1.0_2020-2023` |
| `nu` | νモデル単体 | `nu_v1.0_2020-2023` |
| `complete` | μ+σ+ν統合モデル | `complete_v2.0_optimized_2020-2023` |

#### 2. version（バージョン番号）

**セマンティックバージョニング**（v{major}.{minor}.{patch}）:

- **major**: 学習アルゴリズムの大幅変更、アーキテクチャ変更
- **minor**: 特徴量の追加・削除、ハイパーパラメータの大幅変更
- **patch**: バグ修正、マイナーな調整

**例**:
- `v1.0.0`: 初期版
- `v1.1.0`: 新特徴量追加
- `v1.1.1`: バグ修正
- `v2.0.0`: Stacking Ensemble導入

#### 3. variant（バリアント）

| バリアント | 説明 | 使用例 |
|-----------|------|--------|
| `base` | 基本版（デフォルトパラメータ） | `mu_v1.0_base` |
| `optimized` | Optuna最適化版 | `mu_v1.1_optimized` |
| `ensemble` | アンサンブル版 | `mu_v2.0_ensemble` |
| `calibrated` | キャリブレーション済み | `mu_v1.0_calibrated` |
| `clean` | データリーク除去版 | `nu_v1.1_clean` |
| `experimental` | 実験的実装 | `mu_v1.2_experimental` |

#### 4. training_period（学習期間）

**フォーマット**: `YYYY-YYYY` または `YYYYMMDD-YYYYMMDD`

**例**:
- `2020-2023`: 2020年1月〜2023年12月
- `20200101-20231231`: 詳細な日付指定

### 命名例

```
✅ 良い例:
  mu_v1.0_base_2020-2023
  mu_v1.1_optimized_2020-2023
  complete_v2.0_ensemble_2020-2023
  nu_v1.1_clean_2020-2023

❌ 悪い例:
  mu_model_20241122_final        # versionが不明瞭
  mu_phase_e_calibrated          # phaseは非標準
  complete_model_2024            # variantと期間が不明瞭
```

### チェック方法

#### 1. 自動チェックスクリプト

```python
def check_data_leakage(feature_list):
    """特徴量リストからデータリークをチェック"""
    forbidden = [
        'finish_position', 'finish_time_seconds', 'win_odds', 
        'place_odds', 'popularity', 'is_win', 'is_place'
    ]
    
    leaked = []
    for feature in feature_list:
        # 過去走データは除外（past_N_*の形式）
        if feature.startswith('past_'):
            continue
        
        # 禁止ワードチェック
        for forbidden_word in forbidden:
            if forbidden_word in feature:
                leaked.append(feature)
                break
    
    if leaked:
        print(f"⚠️  データリーク検出: {leaked}")
        return False
    else:
        print("✅ データリークなし")
        return True
```

#### 2. 手動チェック項目

- [ ] 特徴量リストを目視確認
- [ ] `finish_`, `odds_`, `popularity` などの文字列検索
- [ ] 過去走データと当該レースデータの区別を確認
- [ ] 時系列の整合性チェック（学習データが評価データより前）

## 🔬 特徴量エンジニアリング：データリーク防止ガイドライン

> [!CAUTION]
> このセクションは特徴量実装時に**必ず**参照すること。データリークは検出困難で重大な精度劣化を引き起こします。

###原則1: 現在のレースデータと過去のレースデータを厳格に区別する

**❌ NG例**: 現在のレースの`passing_order`や`last_3f_time`を直接使用
```python
# データリーク！レース後にしか判明しない情報
df['horse_early_speed_index'] = df['passing_order_1'] / df['head_count']
df['horse_late_speed_index'] = df['last_3f_time'] / df['distance_m']
```

**✅ OK例**: 過去走データから各馬の傾向を計算
```python
# 過去のパフォーマンスから馬ごとの平均的な特性を計算
performance_df['early_speed_index'] = performance_df['passing_order_1'] / performance_df['head_count']
horse_early = performance_df.groupby('horse_id')['early_speed_index'].mean().reset_index()
horse_early.columns = ['horse_id', 'horse_early_speed_index']
df = df.merge(horse_early, on='horse_id', how='left')
```

### 原則2: 「レース前に取得可能か?」を常に自問する

特徴量を実装する際、以下を確認:

1. **取得タイミング**: この情報はレース開始前に入手可能か?
2. **データソース**: この値はどこから来るか? (出馬表 vs レース結果)
3. **時系列整合性**: 過去データのみを参照しているか?

### 原則3: レース結果データを含むカラムリスト

以下のカラムは**絶対に特徴量として使用禁止**:

#### レース結果 (Race Results)
- `finish_position`, `finish_time_seconds`, `margin_seconds`
- `passing_order_1/2/3/4` (現在のレース)
- `last_3f_time`, `time_except_last3f` (現在のレース)
- `pace_index`, `position_change_*`, `final_corner_to_finish`

#### 確定オッズ (Final Odds)
- `win_odds`, `place_odds`, `final_odds`
- `popularity` (最終オッズから計算)
- `win_probability` (オッズ由来)

#### 派生データ (Derived Data)
- `is_win`, `is_place`, `return_amount`
- `popularity_finish_diff` (結果データとの差分)

### 原則4: 過去走データの正しい使用法

**✅ 許可される使用法**:
```python
# 過去N走の統計量
performance_df.groupby('horse_id')['finish_position'].apply(lambda x: x.tail(10).mean())

# 前走との比較
last_race = performance_df.groupby('horse_id').last()
df = df.merge(last_race[['distance_m']], on='horse_id', suffixes=('', '_prev'))
df['distance_change'] = (df['distance_m'] - df['distance_m_prev']).abs()
```

**❌ 禁止される使用法**:
```python
# 現在のレースと過去のレースを混同
all_races = pd.concat([current_race_df, performance_df])  # 危険!
stats = all_races.groupby('horse_id').mean()  # 未来情報が含まれる
```

### 原則5: morning_odds vs win_odds の区別

| 項目 | `morning_odds` | `win_odds` |
|------|---------------|-----------|
| タイミング | 前日発表 | レース直前 |
| 使用可否 | ✅ OK (予測時に取得可能) | ❌ NG (未来情報) |
| 用途 | 特徴量として使用可 | 評価時のROI計算のみ |

### 特徴量実装チェックリスト

新しい特徴量を実装した際、以下を確認:

- [ ] `performance_df`(過去走)と`df`(現在のレース)を明確に区別している
- [ ] 現在のレースの結果データ(`finish_position`, `last_3f_time`など)を直接使用していない
- [ ] `groupby`操作で未来データが混入していない
- [ ] morning_oddsのみ使用し、win_oddsは使用していない
- [ ] 時系列順にソートし、`.shift()`や`.tail()`を適切に使用している
- [ ] テストスクリプトで特徴量生成を検証し、値の妥当性を確認している

### データリーク検出の実例

**2024-11-24に発見された実例**:

```python
# ❌ データリーク発見: generate_pace_features が現在のレースデータを使用
def generate_pace_features(self, df: pd.DataFrame) -> pd.DataFrame:
    # currentレースの passing_order を直接使用 → データリーク!
    df['passing_order_1'] = df['passing_order'].apply(get_first_passing)
    df['horse_early_speed_index'] = df['passing_order_1'] / df['head_count']
```

**修正後**:
```python
# ✅ 修正: 過去走データから計算
def generate_pace_features(self, df: pd.DataFrame, performance_df: pd.DataFrame) -> pd.DataFrame:
    # 過去走の passing_order から馬ごとの傾向を計算
    performance_df['passing_order_1'] = performance_df['passing_order'].apply(get_first_passing)
    performance_df['early_speed_index'] = performance_df['passing_order_1'] / performance_df['head_count']
    
    # 各馬の平均値を特徴量として使用
    horse_early = performance_df.groupby('horse_id')['early_speed_index'].mean().reset_index()
    df = df.merge(horse_early, on='horse_id', how='left')
```

### バージョニングのベストプラクティス

1. **命名規則**: `v{major}{minor}_{variant}`（例: `v26_restored`, `v27_experimental`）
2. **不変性**: 一度作成したバージョンフォルダは原則として変更しない。改善は新バージョンで行う
3. **比較可能性**: 同一条件（テスト期間、データ範囲）で評価した結果を記録
4. **失敗記録**: 「何がうまくいかなかったか」を `development_log.md` に記録（将来の無駄な試行を防ぐ）
5. **参照リンク**: 各 `report.md` から関連ドキュメント（`23_包括的検証レポート_v3.md` 等）へのリンクを記載
