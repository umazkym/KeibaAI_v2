# データベース現状分析レポート

**作成日時**: 2026-04-03
**目的**: KeibaAI_v2プロジェクトのローカル環境内に、現在どのようなデータが物理的に保存され、どのような構成になっているかを網羅的に調査した結果をまとめる。

---

## 1. 保存アーキテクチャの概要

現在のプロジェクトでは、データベースとして主に **Parquetファイル** と **SQLite** の2層アーキテクチャが採用されています。

1. **SQLite (`data/metadata/db.sqlite3`)**
   - ファイルサイズ: 約5.8 MB
   - 用途: 主にスクレイピングの進行状態管理、各レースIDや馬IDのインデックス、作業メタデータなどが格納されているワーク用データベースです。
   - 同梱ファイル: `horse_id_list.txt` などのスクレイピング対象リストが併せて保存されています。

2. **Parquet群 (`data/parsed/` および `data/features/`)**
   - 列指向フォーマットであるParquetが、大容量データの高速読み込みと機械学習への連携という主要なデータベース（DWH）の役割を果たしています。

---

## 2. 実データ（Parquetテーブル）の分析

`data/parsed/parquet/` 配下を調査したところ、`03_データモデル.md` で定義されているコア・データ群に加えて、**ドキュメント外の派生データや試験的データ群**も大量に存在していることが判明しました。

### 2.1 コア・データベース（ドキュメント定義済みデータ）
概ね2020年〜2024年（あるいは2025年）の数十万レース規模のデータが蓄積されています。
*   **races** (`races.parquet`): 約34.1 MB
    *   全レースのヘッダ、着順、タイム等のマスタ。過去のバックアップファイルも複数存在します。
*   **shutuba** (`shutuba.parquet`): 約11.3 MB
    *   各レースの出馬・オッズ・斤量などの情報。デバッグや一時出力とみられる `shutuba_temp.csv` (約37 MB)も同居しています。
*   **pedigrees** (`pedigrees.parquet`): 約13.6 MB
    *   各馬の5代前までの血統データテーブル。1頭あたり多数のレコードを持つため比較的ファイルサイズが大きくなっています。
*   **horses** (`horses.parquet`): 約1.8 MB
    *   馬のプロフィール（生年月日、調教師など）。
*   **race_details / corners** (`race_details.parquet` 5.5MB, `corner_positions.parquet` 3.2MB)
    *   ラップタイムやコーナー通過順位などの詳細推移データ。
*   **returns** (`returns.parquet`): 約2.8 MB
    *   単勝や3連複など、各賭け式の払い戻し金額マスタ。

### 2.2 派生/拡張データベース（ドキュメント外データ）
システムドキュメント（第2版）の記載にはない以下のデータセット・テーブル群が構築されています。

*   **地方競馬データ (`nar_races/`)**
    *   約185個の日次ファイル (`nar_races_20250101.parquet`等) と結合済みの `nar_races_combined.parquet` (約1.5 MB) が存在します。
    *   JRA（中央競馬）だけでなく、NAR（地方競馬）のデータを独立して収集・管理するパイプラインが存在しています。
*   **成績集計データ (`horses_performance.parquet`)**
    *   ファイルサイズ: 約28.8 MB （修正版の `_fixed.parquet` は約11.0 MB）
    *   各馬の過去の成績に関する高度な集計指標（走破タイム偏差や着順実績など）を事前に計算し、特徴量生成を高速化するための中間マスタテーブルと推測されます。
*   **時系列オッズデータ (`odds/`)**
    *   `tansho_fukusho`, `umaren`, `wide`, `sanrenpuku`, `sanrentan`, `umatan` のように券種ごとのサブディレクトリに分かれています。
    *   `tansho_fukusho/202401010101.parquet` のように、**レースIDごとに個別のファイル単位で保存**されている構造です。ただし現在は一部レース分（数十個）のみ存在しており、直前オッズの時系列予測や実験的なトラッキングシステムの残骸/プロトタイプである可能性が高いです。
*   **分析ベーステーブル (`analysis/base_table.parquet`)**
    *   ファイルサイズ: 約0.9 MB
    *   特定の一時的な分析（EDA）用に複数のテーブルを JOIN し抽出したベーステーブルが存在します。

## 3. 機械学習用 特徴量データベース

`data/features/parquet/` 内に構成されています。

*   **データ構造設計**: `year=2020` から `year=2024` までの年別ディレクトリによる **Hiveスタイルのパーティショニング**がおこなわれています。これにより、学習時にメモリを圧迫せずに特定期間のデータのみを高速に絞り込んで遅延読み込み（Pandas/PyArrow）を行える設計になっています。
*   **スキーマ管理**: `feature_names.yaml` によって、機械学習モデルに投入される特徴量のカタログリストが管理されています。

---

## 4. 総評・まとめ

現在のローカルデータベースは、単なるスクレイピング結果の保存場所という域を超え、**「本番モデル学習用の時系列パーティション化された特徴量基盤」**として既に高度に整理・構築されています。

また、`03_データモデル.md`に書かれている以外に、
1. 事前集約によるパフォーマンス改善 (`horses_performance.parquet`)
2. 時系列オッズの収集実験の痕跡 (`odds/` 構造)
3. 地方競馬への拡張の痕跡 (`nar_races/`)

などが物理データとして残されていることが確認できました。これらドキュメントと実データの乖離部分は、コードベースを拡張やリファクタリングする際に考慮・整理すべきポイントとなります。
